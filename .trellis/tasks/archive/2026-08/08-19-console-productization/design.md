# 技术设计：控制台产品化

## 1. 边界：这次改的是「呈现层」，不是「配置内核」

一条贯穿全文的不变量：**配置字段仍且只能从 `getPanelFields()` 自省派生**（父 PRD R3 / KT-DEC-0035）。本次新增的一切分层、预设、折叠都是**呈现层的装饰**，不得成为字段的第二个真源。

落成一条可测的规则：

> **未知键降级可见，而不是消失。** 呈现注册表只登记「哪些键提升为常用」「哪些键归入某预设」。任何未登记的键**自动落入「高级」并照常渲染**。
> 于是往 schema 加一个新字段时，它仍然自动出现在界面上（只是在高级区），**不会因为忘了改呈现注册表而静默消失**——静默消失正是 KT-DEC-0035 当初要防的。

同理，写入仍走既有 `writeFieldValue`（`fabric config` 用的同一个函数），一个 key 一个 home（KT-MOD-0004）。

## 2. 作用域模型

### 2.1 表示
作用域是一个值：`machine` 或某个 `projectId`。

- 传输：URL 查询参数 `?scope=machine|<projectId>`（可分享、可刷新、可后退）。
- 持久：`localStorage`，只作为**默认值**，URL 参数优先。
- 服务端解析：`scope=<projectId>` → 查机器级注册表拿绝对路径 → 该路径即该请求的 `projectRoot`。

### 2.2 服务端契约
`scope` 是**每个请求的参数**，不是服务器启动态。`startPreviewServer` 的 `projectRoot` 退化为「默认作用域」。

| 端点 | 变化 |
| --- | --- |
| `GET /api/scopes` | **新增**。返回 `machine` + 已登记项目（含 `stale`），供切换器渲染 |
| `GET /api/status?scope=` | 参数化。`scope=machine` 时返回**跨项目总览**（版本三处、项目列表、挂载库），而非单项目状态 |
| `GET /api/knowledge?scope=` | 参数化。`scope=machine` 时……见 2.4 |
| `GET /api/config?scope=` | 已是机器视角；`scope=<项目>` 时把该项目行置顶并默认展开 |
| `GET /api/integrations?scope=` | **新增**。见 §4 |
| `POST /api/config/set` | 已有。新增 `action:"reset"` 语义，见 §3.3 |
| `POST /api/config/preset` | **新增**。批量应用一个预设，见 §3.2 |
| `POST /api/repair` | **新增**。见 §4.3 |

### 2.3 解析失败必须是显式状态
`scope=<projectId>` 指向的路径已不存在（`stale`）或该 id 只在全局配置里有段落而无路径（`config-only`，KT-PIT-0050 决定这类 id **永远**拿不到路径）时：

不回退到默认作用域——静默回退会让用户以为自己在看 A 项目而其实在看 B。返回 `409` + 明确原因，页面渲染「这个项目的目录已不在原处 / 这个项目从未登记过路径」以及下一步（`fabric install` 重新登记）。

### 2.4 `scope=machine` 下的知识视图与既有 `--all` 的关系
两者都会被用户读成「全部」，必须在一次设计里定死：

- `--all` / `?all=1`（KT-DEC-0079）= **所有挂载的 store**，回答「这台机器上我有哪些知识库」。
- `scope=machine` = **所有已登记项目的 read-set 并集**，回答「我的项目们各自能看到什么」。

结论：**machine 作用域下的知识页直接复用 `--all` 的「按库浏览」语义**，不再造第三种聚合。切到具体项目时才是该项目的 read-set。界面上二者用不同措辞（「按知识库浏览」vs「本项目可见」），不出现两个都叫「全部」的东西。

## 3. 设置页

### 3.1 三层信息架构
1. **常用**（约 6 项）：语言、归档提醒频率（预设卡）、语义检索、编辑前检索、AI 自动提议归档、活动日志保留。
2. **高级**（默认折叠，约 9 项）：检索排序、默认检索范围、审计模式、知识库门槛、三项冷却参数等。
3. **搜索**：一个输入框跨两层过滤（VS Code 的做法）。搜索命中高级项时**自动展开高级区**——否则搜索会「什么都搜不到」。

来源层不再是标题旁的标签：**改过的项左侧一道 3px 竖条**，来源层降为悬停/详情内容。

### 3.2 预设（归档提醒频率）
- 预设定义 = `{ id, label, values: Record<PanelFieldKey, unknown> }` 的**常量表**，与呈现注册表同处一文件。
- 应用：`POST /api/config/preset` 在**服务端**逐键走 `writeFieldValue`（复用既有校验与 home 路由），**不新增写入路径**。要么全成功，要么把已成功的键与失败键都报出来——不假装原子。
- 反向识别：读取时把当前生效值与各预设逐键比对，全等则显示该预设，否则显示「自定义」。**不落任何 `preset_name` 字段**——落了就是第二个真源，会与实际值漂移。
- 预设覆盖的 8 个键在高级区仍可逐项修改；改完自动变「自定义」。

### 3.3 恢复默认（补上现有缺口）
现状：per-project 覆盖加得上、删不掉（上一轮实测）。
新增：`POST /api/config/set` 接受 `action:"reset"` → 在**目标层**删除该键（machine 删 `defaults[key]`，project 删 `projects[<id>][key]`，store 删 store-config 键），再重新 resolve 返回。删到空段落时一并删除空对象，避免留下 `{}` 垃圾。

### 3.4 新增的三项可配置面
| 项 | 落点 | 注意 |
| --- | --- | --- |
| `hint_dismiss_signals` | preference | 呈现为「不再提醒这类事」的多选，值域来自实际发出的信号名，不硬编码 |
| `embed_endpoint` / `embed_model` | global_root | key 只显示「已设置 / 未设置」+「重设」，**永不回显原文**（现有约定） |
| `active_write_store` | 项目配置 | 只在项目作用域可改；选项来自该项目已绑定的 store |

`embed_*` 与「语义检索」联动出「已启用 · 未生效」状态：`embed_enabled=true` 但嵌入服务不可用时，如实标注并给出下一步，而不是只显示 `true`。

## 4. 集成页（新）

### 4.1 数据来源全部是既有真源
| 展示 | 真源 |
| --- | --- |
| 客户端是否接入 | 该客户端配置文件中是否存在 Fabric 的 MCP 条目 |
| hook 装了哪些 / 是否漂移 | `.fabric/install-manifest.json` 的文件 hash 对模板实际内容 |
| skill 装了哪些 | 文件系统（模板目录 ↔ 安装目录），**不读任何布尔清单** |
| 托管块是否同步 | manifest hash 比对 |
| 运行时行为开关 | **既有 config key**（`cite_policy_enabled` 等） |

### 4.2 「行为」而非「文件」
界面上的开关单位是**用户能判断的行为**（「编辑前提示检索」），其真源是既有 config key。物理文件（`knowledge-pretooluse.cjs`）只出现在详情里，且**只读**。

这条不是审美选择：给分发清单加「装不装」的布尔标记会造出第三份真相（KT-PIT-0067 实证：install spec 一份、uninstall 一份、文件系统一份，结果「装下去的 skill 让 AI 打开一个从未被写入的文件」而测试全绿）。

### 4.3 一键修复
`POST /api/repair` 只有两个受限动作：`install`（重装本项目的物件）与 `doctor --fix`。

- 目标由服务端从作用域推导，**请求体不带路径**（沿用写通道的「请求永不携带路径」规则）。
- 子进程输出流式回传并在页面上可见——「升级动作的输出可见，不是黑箱等待」（父 R4）。
- `machine` 作用域下不提供修复：修复总是针对某个具体项目。

## 5. 复用与新增边界

- `shell.css` 仍是设计令牌唯一来源；切换器、竖条、开关行、折叠区属于**跨页原子**，进 shell.css；单页布局留在各自模板。
- `lumen.html` 不迁令牌（已知有界债务），只改：navbar 挂切换器、取数带 `scope`。
- 每页仍是独立路由 + 独立模板（KT-DEC-0080）。
- 零构建前端不变（C2）。

## 6. 风险与回滚

| 风险 | 处理 |
| --- | --- |
| 呈现注册表与 schema 漂移 → 新字段消失 | 未知键落「高级」；加一条测试：往字段表塞一个未登记键，断言它出现在高级区 |
| 预设识别逻辑写反 → 显示「标准」但实际值不是 | 逐键全等比对 + 一条变异测试（改任一键的值，断言显示变「自定义」） |
| `scope` 解析回退 → 看错项目 | 显式 409，不回退；测试覆盖 stale 与 config-only 两种失败 |
| `/api/repair` 触发子进程 | 仅 loopback + POST + 同源 Origin 校验（既有写通道守卫），动作枚举封闭，无路径入参 |
| 知识页改动触发只读回归 | 既有 preview-* 测试全绿是硬门槛（父 AC5） |

回滚点：作用域参数化（§2）、设置页重排（§3）、集成页（§4）三块相互独立，可各自单独回退。
