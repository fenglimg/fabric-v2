# Design — 仓库门面整洁化

## 0. 贯穿全篇的一条原则

本任务全部改动**必须行为等价**。所以每一项都要能回答同一个问题:
**「如果我把这次改动做错了,哪条判据会红?」** 答不上来的项不做 —— 那是 KT-GLD-0019
(测试价值只认变异判据)在重构上的直接推论: 没有判别力的改动等于没有保护的改动。

---

## R1 · `packages/cli/C:` 垃圾 + `tmp/` 忽略规则收窄

### 现状(实测)

```
.gitignore:139   tmp/          ← 无前导斜杠 = 匹配任意深度
packages/cli/C:/tmp/fabric-project/...   160 个文件,被上面这条吃掉
```

`git check-ignore -v` 已确证匹配来源。后果是**垃圾对 `git status` 隐身**。

### 设计

两步,**顺序不可换**:

1. **先删** `packages/cli/C:`(整棵)。它是 Windows 绝对路径 `C:\tmp\...` 在 POSIX 下被当成
   相对目录创建的产物 —— 某个测试没有正确处理平台路径。
2. **再把规则改成 `/tmp/`**。前导斜杠把它锚定到仓库根,只挡那个 535MB 的外部克隆目录
   (规则原注释写明的本意就是这个)。

顺序不可换的原因: 先改规则会让 160 个文件立刻变成 untracked 噪声,污染 `git status`,
在删除完成前一直干扰其他判断。

### 判别力(改错了什么会红)

A2 是一条**构造式断言**,不是观察式的:

```bash
mkdir -p packages/cli/__probe__/tmp && touch packages/cli/__probe__/tmp/junk
git status --porcelain -uall | grep -q 'packages/cli/__probe__/tmp/junk'   # 必须命中
git check-ignore -q tmp                                                    # 根目录仍必须被忽略
rm -rf packages/cli/__probe__
```

**两条都要**: 只验前者会让「把规则整条删掉」这种错误通过;只验后者会让「规则没改」通过。

### 遗留问题(不在本任务修)

`C:` 是**某个测试写出来的**。删掉它只是清理症状,源头没堵。本任务不追这个源头(属行为域,
超出门面范围),但 A2 的构造式探针会让它下次复发时**立刻可见** —— 这正是把「隐身」改成
「可见」的价值所在。**在收口记录里明确列为已知遗留,不要让它看起来像已解决。**

## R2 · `assets/` / `schemas/` 顶层格位

### 实测

| 路径 | 内容 | 仓内引用 | 在 `files[]` | 结论 |
|---|---|---|---|---|
| `assets/brand/*.svg` | 2 个品牌 SVG | **0** | 否 | 仓内确无消费者 |
| `schemas/fabric-config.json` | JSON Schema,`$id` 是假 URL `https://fabric.local/...` | **0 个真消费者** | 否 | 无人 `$schema` 指向它 |

`fabric-config.json` 那 159 处「命中」全是运行时的 `.fabric/fabric-config.json` ——
**同名不同物,典型的名字探针撒谎**(KT-PIT-0073)。22 处 `schemas/fabric-config` 命中
全是 research 文档 / CHANGELOG / issues 在**谈论**它,没有一个是消费者。

### 设计:两者处置**不同**,不要一刀切

- **`schemas/`** —— 无消费者、未发布、`$id` 指向一个不存在的域名。它是一份**声称自己是契约
  但没有任何东西按它校验**的文件。参照 KT-PIT-0065/B6 的既有判例(「没人拿来 parse 的
  schema 比没有更糟」),**倾向删除**;但删前必须先确认它与 `packages/shared` 里的
  zod schema 是否存在「谁是真源」的关系 —— 若 zod 才是真源,这份 JSON Schema 就是
  dual-truth,删它是**修复**而不只是清理。
- **`assets/`** —— **默认不删**。品牌资源的消费面(GitHub 组织头像 / npm 页面 / 站点)
  **结构上不在仓内留痕**,「查不到引用」在这里不是死亡证明。按 KT-GLD-0016
  rescue-before-delete,可选动作只有「归位」(如并入 `docs/` 或 `packages/cli/templates/`),
  且需要先向用户确认这两个 SVG 是否有仓外用途。

### 判别力

删 `schemas/` 后:`pnpm lint`(knip) + `lint-dangling-refs` + 全套测试必须仍绿,
且 `git ls-files | grep -c schemas/` 归零。若有任何一处红,说明引用普查漏了面。

## R4 · `server/src/services/` 平铺治理(B10 重议)

### 先记录翻案

B10 于 **2026-08-12 上午**被判「审计后不做」,理由是「提案自陈纯移动、零行为收益、
断 blame」。**本任务翻案。** 翻案依据不是新证据,是**价值函数变了**:
当时的裁决只在「正确性 / 缺陷密度」一个维度下称量;用户随后明确把「工程美感 /
一眼看到结构」提为一等诉求。按 KT-GLD-0011,旧决策的 rationale 不再适配当前需求时
不得拿它挡。**roadmap 与本文件双向记录,不静默改口。**

### 实测形状(比 roadmap 记的更糟)

| 口径 | roadmap 记的 | 实测 |
|---|---|---|
| 目录条目 | 96 文件 | **179**(源码 97 / 共址测试 80 / 目录 2) |

### ⚠️ 原方案「按前缀落子目录」经数据检验**不成立**

一级前缀分布:

```
doctor 48 | review 8 | plan 8 | 然后是 30 个只有 1 个文件的前缀
```

**只有 3 个前缀够格建目录,剩下 30 个是单例。** 按前缀分的结果是
3 个目录 + 30 个无处可去的散件 —— 杂乱没消失,只是换了个形状。

### 设计:分组必须从 **import 图**推导,不从文件名猜

这是本任务最容易犯错的一步,而且犯错方式是熟悉的那个: **按名字分组 = 按「读起来像什么」
分组**,而正确的依据是「它实际和谁耦合」(轨F 四次同类错误的同一教训)。

**流程(实施阶段执行,此处只定契约)**:

1. 用静态 import 图算出 97 个源文件的**耦合簇**(谁 import 谁,双向)。
2. 簇 = 候选目录。**只接受满足两条的簇**: ① ≥4 个文件;② 簇内耦合明显高于簇间。
3. 不满足的文件**留在 `services/` 顶层** —— 这是刻意的:一个诚实的「3 个目录 + 20 个散件」
   好过一个「10 个目录,其中 7 个是为了消灭散件硬凑的」。**硬凑出来的目录名会撒谎。**
4. **共址测试跟着它测的源文件走**,不单独归类(KT-PIT-0080:server 的共址布局是
   `rootDir` 约束下的正确选择,不是待修的漂移)。

### 判别力(这一步最关键)

纯移动最危险的失败模式是「测试还是绿的,但少跑了一批」。所以:

| 判据 | 为什么这条能咬 |
|---|---|
| **逐包测试用例数与改动前完全相等** | 只看「全绿」会放过「某个测试文件没被 glob 到」 |
| `tsc --noEmit` 退出 0 | 移动改 import 路径,类型层是第一道 |
| **迁移前先普查 `scripts/` + `.github/workflows/` + `package.json` npm scripts** | 已有判例:改路径漏迁这三处 → 本地全绿 CI 红 |
| `git mv` 而非 rm+add | 保住 rename 检测,blame 可经 `--follow` 追 |
| `knip` 无新增未用项 | 移动时误留旧文件会被它抓到 |

## R5 · 三包测试布局(设计阶段裁决)

实测:

| 包 | 共址 `src/` | 独立目录 |
|---|---|---|
| shared | 9 | 45 |
| server | **94** | 8 |
| cli | 0 | 144 |

**裁决: 不统一,改为显式文档化。** 理由: KT-PIT-0080 已论证 server 的共址是
`tsconfig` `rootDir: ./src` 约束下的**正确选择** —— 强行统一要么破坏 server 的类型检查,
要么要连带搬走数千行大测试文件。而 cli 的 `__tests__/` 压根不在 `include` 里,
两个包的差异**有原因,不是待收敛的漂移**。

**可接受解**: 在 `docs/TESTING.md` 增补一节,写明三包各自的布局与**为什么**,
并把 shared 那 9 个共址例外核一遍(它是唯一没有原因说明的骑墙者)。

判别力: 弱(文档改动)。因此这一项**不设硬判据,只要求 `lint-dangling-refs` 仍 PASS**,
并明确它属于低价值项 —— 若实施阶段时间紧,这条第一个砍。

## R6 · `.trellis/` 跟踪面(设计阶段裁决)

`.trellis/` 102 个跟踪文件 = `scripts`+`docs`+`.github`+`.fabric` 之和的 2.4 倍,
构成「为了引进而引进」感受的可测来源。

**裁决: 本任务只做评估,不动。** 理由:

- `.trellis/tasks/`(22) 是**本项目自己的**规划产物,删了就丢真信息 —— 不是引进物。
- `.trellis/spec/`(42) + `scripts/`(28) 是 Trellis 的**升级载体**(带 `.template-hashes.json`
  校验)。不跟踪它们会让升级机制失去比对基准,属于**动上游工具的契约**,超出本任务范围
  (PRD §2.2 已显式排除)。
- 真正该问的问题是「本仓要不要继续用 Trellis」,那是产品决策不是清理动作。

**产出**: 在收口记录里把这个数字与结论写下来,让下次有人再感到「臃肿」时,
不必重新量一遍就能知道**这部分是有意保留的**。
