# Fabric 控制台（后端 + 管理界面）

## Goal

给 Fabric 一个本机运行的管理界面，让「Fabric 当前在按什么规则跑、配置最终生效值是什么、机器上哪些项目装了它、哪些落后了」变成看得见、改得动的东西。

CLI 仍然是唯一的生效内核；控制台是它的展示面与操作面，**不新增第二套业务逻辑**。

## 动机：产品化与易用性（用户明示，2026-08-17）

做这套界面的本质诉求不是「补功能」，而是**产品化与易用性**——让 Fabric 从「作者自己会用的工具」变成「别人装上也能上手的产品」。

这条动机改变验收标准，不只是背景色彩：

- 判据从「信息查得到」升级为「**第一次打开就看懂**」。一个需要看文档才能理解的面板，在自用工具里合格，在产品里不合格。
- 空状态、失败状态、数据不全的状态都必须**主动说明原因和下一步**，不能只是空白或一个报错码。典型：存量项目尚未登记时列表不全，页面必须讲清「为什么少」和「怎么补」，而不是让用户误以为自己只有这几个项目。
- 术语要用用户的话。`semantic_scope` / `read-set` / `write-target` 这类内部词进界面前需翻译。
- 界面不得成为使用 Fabric 的前置条件（AC6）——产品化意味着降低门槛，不是增加一个必须先跑起来的组件。

这条动机同时划出一条**反向边界**：产品化的对象是 Fabric 现有能力的可达性，不是借机扩功能面。功能边界仍受 C1 约束（知识层 only）。

## 背景：为什么现在做（基于代码实证，非推测）

| 用户提的诉求 | 代码实情 | 性质 |
| --- | --- | --- |
| ① fabric preview 端口展示 | `fabric preview` 已存在：127.0.0.1:7777，只读，按 semantic_scope 分组，轮询 `/api/revision` 自动刷新 | **已有地基**，需扩为多页 |
| ② CLI 配置效率低 | `fabric config` 已是 clack 交互面板，且配置项可自省（`getPanelFields()`） | **引擎已有**，缺「生效值 + 来源」可视 |
| ③ 版本/安装管理 | `.fabric/install-manifest.json` 记录 `fabric_version` + 文件 hash；但 `~/.fabric/state/bindings/` 只有 project_id UUID，**无仓库路径** | **内核缺能力**，必须先补 |
| ④ 其他展示面 | `doctor`/`audit`/`info`/`metrics`/`sync` 多数已有 `--json` | **已有数据源**，包一层即可 |

实测漂移证据（2026-08-17）：npm 最新 `2.6.0` / 全局 CLI `2.5.0-rc.4` / 本 repo manifest `2.5.0-rc.4`。三者已不一致，且用户当前无任何界面能发现这件事。

## Requirements

### R1 项目注册表（→ 子任务 console-project-registry）
- `fabric install` 成功后，把该仓库的绝对路径登记到机器级注册表。
- 注册表以 `.git` 为项目根锚点（对齐 KT-DEC-0050，禁止用 `.fabric` 当锚——散落残留会自我俘获）。
- 记录至少：repo 路径、project_id、上次 install 的 fabric 版本、上次登记时间。
- 路径失效（目录被删/移动）时可被识别为 stale，不静默留脏数据。
- 存量项目：提供把已有项目补登记的路径（用户已选「install 时登记」，存量靠各跑一次 install 或手动添加）。

### R2 控制台骨架（→ console-shell）
- `fabric preview` 扩为多页控制台，保留现有 Lumen 视觉风格（用户明确认可）。
- 每个功能页是**独立的服务端路由 + 独立模板**，不靠往既有模板注入数据改写实现（KT-DEC-0080 原则）。
- 引入写通道：仅监听 127.0.0.1，不做鉴权（用户已决策）。
- 写操作必须有明确的失败反馈，不静默吞错。

### R3 配置视图（→ console-config-view）
- 展示每个配置项的**最终生效值**及其**来源层**（env / repo / global / store / 代码默认值）。
- 字段列表从 `getPanelFields()` 自省派生，**禁止手写静态字段清单**（KT-DEC-0035 原则：加字段自动出现、删字段自动消失）。
- 可编辑：写入该 key 的唯一归属层（KT-MOD-0004：一个 key 只能有一个可写位置，绝不双写）。
- 需核实并如实呈现 `STORE_OVERRIDABLE_KNOBS` 声明与实现的差异（KT-PIT-0081 记录声明 15 组、实际 12 组生效）——界面必须显示实际生效的，不能照抄声明。

### R4 版本与升级（→ console-version-upgrade）
- 总览：npm 最新版 / 全局 CLI 版本 / 每个已注册项目的 install 版本，落后项高亮。
- 支持对选中项目触发重跑 `fabric install`。
- 升级动作的输出可见（不是黑箱等待）。

## Constraints

- **C1 不做编排器**：Fabric 的产品边界是知识层（KT-DEC-0072）。控制台只管 Fabric 自身的配置/安装/知识展示，不扩成通用任务面板。
- **C2 零构建前端**：沿用单文件 HTML + 系统字体、无外部依赖、离线可用（用户已决策）。不给 CLI 发包引入前端构建链。
- **C3 只听 loopback**：任何情况下不得绑 0.0.0.0。
- **C4 install 幂等性**：注册表写入发生在幂等命令里，必须能承受重复执行；不得用「一次性时间戳」语义（KT-PIT-0076 实证：幂等命令里的 once-ever 盖戳会被每次重跑重置，导致依赖它的功能永不触发）。dry-run 不得写注册表。
- **C5 双根布局**：注册表是本机状态，落 `~/.fabric`，永不入 repo git（KT-DEC-0003）。
- **C6 install 阶段输出纪律**：新增 stage 不得自己 `console.log` 旁白行，rich detail 走 `StageResult.detail`（KT-DEC-0044）。

## Acceptance Criteria（父任务：跨子任务的整体验收）

- [ ] AC1 装完后打开控制台，能在一屏内看到：本机 Fabric 版本、npm 最新版、已注册项目列表及各自版本状态。
- [ ] AC2 至少一个配置项能在界面上改，改完 `fabric config --list`（CLI 侧）读到同样的值——即 UI 与 CLI 共用同一份真值，无第二套状态。
- [ ] AC3 对一个落后的项目从界面触发升级，完成后该项目的 `install-manifest.json` 里 `fabric_version` 与全局 CLI 一致。
- [ ] AC4 配置页展示的「生效值/来源层」与实际 resolve 结果一致，含至少一个 env 覆盖 repo 的用例（对齐 KT-PIT-0062 教训：断言值不得恰好等于代码默认值，否则用例假绿）。
- [ ] AC5 现有 `fabric preview` 的只读知识浏览行为不回归（既有 preview-* 测试全绿）。
- [ ] AC6 关闭控制台后，CLI 全部命令行为不变——控制台不是任何 CLI 能力的前置条件。
- [ ] AC7（产品化）每个页面在「空数据 / 数据不全 / 获取失败」三种状态下，都显示原因与下一步动作，而非空白或裸错误码。
- [ ] AC8（产品化）界面不出现未翻译的内部术语；一个没读过 Fabric 文档的人能说出每个页面在讲什么。
