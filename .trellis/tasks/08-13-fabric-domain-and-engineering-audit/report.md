# Fabric 深审报告 —— 领域最佳性与工程完美度

审计日期 2026-08-13 · 版本 `2.5.0-rc.4` · 分支 `main`

> ⚠️ **限定**:本报告**未经零上下文外部复核**,判定的乐观偏差未被独立消除。用户已决定不将报告发往外部模型;W5 采用本地对抗复核,强度低于冷评。本仓实测过同一 agent 自评 100% vs 零上下文冷评 81%(`KT-GLD-0006`),该 gap 在此仍可能存在。

---

## 0. 两个判定,先给结论

### 问题一:Fabric 是它所在领域最好的项目吗?

**判定:否 —— 但在一个被自己划得很窄的窗口里,它是最好的。**

一句话理由:在"团队审过的知识 + 完整生命周期治理"这个窄口径上 Fabric 确实领先;但按用户真实痛点("AI 反复违反已定规矩")重新划线,**Mneme HQ 在"能不能提供保证"这条轴上更强**,**Basic Memory 在生态上强出两个数量级**,而 Fabric 零外部用户。

### 问题二:它的工程实现完美吗?

**判定:有条件是 —— 门禁下无缺口(P1 成立),但门禁本身有真实漏洞(P2 不成立)。**

一句话理由:13 道门禁 12 道绿、3310 个测试通过、依赖面极简、分层零反向依赖 —— 这是**明显高于平均水准**的工程。但审计实测出一道门禁自身是坏的、一处核心契约校验可被掏空而 3310 个测试无一察觉。**"完美"不成立,"优秀"成立。**

## 1. 领域对标

> **这节在看什么**:同类工具里,Fabric 站在哪。看不好会怎样 —— 你会以为自己在造一个没人做过的东西,实际上别人已经做到了下一站。

完整候选普查见 [`research/domain-census.md`](research/domain-census.md)(四类、20+ 候选,逐个标 in/out)。

### 1.1 六轴对标

| 轴 | Fabric | 最强对手 | 证据 |
| --- | --- | --- | --- |
| 问题域契合度 | **领先** | team-memory-mcp | 五类强 schema + pending→review 人工闸门;对手只有 Bayesian 置信度,无类型、无审批 |
| 生命周期完整性 | **领先** | KCS(理论)/ Basic Memory | draft→verified→proven + retire + 降级 + `KT-PRO-0001` 晋升 rubric(≥30 天、related 入度 ≥3、机械信号永不自动升);Basic Memory 无生命周期状态机 |
| 跨客户端可移植性 | **持平偏后** | Basic Memory | Fabric 支持 2 端(Claude Code + Codex);Basic Memory 覆盖 Claude / Codex / Cursor / ChatGPT / VS Code / Obsidian |
| 首次到价值成本 | **落后** | 裸 CLAUDE.md | Fabric 要 install + store bind + switch-write,还要理解 scope 三轴;`KT-DEC-0072` 自己把"首价值闭环"列为未完成待办,承认"装完无命中感知、激活失败"是已知风险 |
| 治理与可审计性 | **有条件领先** | Mneme HQ | Fabric 的**审批链**更强;Mneme 的**执行力**更强(PreToolUse exit 2 硬阻断 + 可重建 verdict + 公开 benchmark)。两者不是同一种治理 |
| 生态与可持续性 | **显著落后** | Basic Memory | 3641 stars / 57K 月下载 / 付费云 / 多插件生态 vs Fabric 零外部用户、单一维护者 |

### 1.2 靶子攻击的结论(PRD R1 硬要求)

对 `KT-DEC-0072` 划的边界("只做知识层,不做 session 记忆、不做编排器")做了三问:

1. **是真判断还是自我服务?** —— 大部分真,一处不真。排除 session memory 有正当理由(两类数据混一起会让审核闸门失效)。但 README 的核心论证**只对比了最弱的对手**(裸 `AGENTS.md`),完全没提 Basic Memory —— 后者同样 Markdown、同样跨客户端、同样 MCP-native,还多了知识图谱和语义检索。把对手设成"一个 markdown 文件",赢面自然大。
   更关键的:检索显示 **"propose-don't-publish"(agent 只写 pending,人工审核才进 canonical)是这个领域已被命名的既有模式**。Fabric 的 pending→review 是该模式的一个实现,**不是一个新范畴**。

2. **按真实痛点,对手是谁?** —— 是 Mneme HQ,不是 memory 产品。而 Fabric 的 `KT-DEC-0007` **主动选择了"只软提醒、不做 permanent gate、不做 decision:block"**。Mneme 走相反的路:PreToolUse hook 拦 Edit/Write,exit 2 直接挡掉违规写入。
   Mneme 的三级阶梯说得很直白:"没进上下文 → 进了上下文但只是建议 → 被确定性检查强制执行",**只有第三级把决策变成保证**。**按这把尺子,Fabric 停在第二级。**
   这不必然是错的选择(硬阻断有假阳性成本,`KT-GLD-0018` 记录过锁死文案的门禁如何变成假红),但它**必须被当作明确的竞争劣势陈述出来**,而不是被"我们不做 gate"的内部决策悄悄消化掉。

3. **边界放宽会怎样?** —— 允许 session memory 进来,Fabric 立刻落后(无时序图谱、无自动事实抽取、无公开 benchmark 分数);允许编排进来,Fabric 是半个产品;只放宽到"含 rules-file 分发",Fabric 位置**变好**(它同时做分发和治理,Plexus/agnix 只做前者)。

**净结论:Fabric 的边界在一个很窄的窗口里最优。窗口越窄,"领域最好"的含金量越低。**

## 2. 工程质量

> **这节在看什么**:代码本身够不够硬。看不好会怎样 —— 你以为有 13 道安全网,其中一道其实是破的,而且破了没人知道。

完整证据与复现命令见 [`research/engineering-evidence.md`](research/engineering-evidence.md)。

### 2.1 P1(门禁下无缺口)—— **成立**

13 道门禁实跑,12 道绿。测试总量 **3310 个通过**(shared 649 / server 1172 / cli 1489)。

复现:

```bash
pnpm -r build && pnpm typecheck && pnpm typecheck:tests && pnpm lint && pnpm test
```

### 2.2 P2(门禁本身够严)—— **不成立**

三条实证:

**F-01 `nofake-audit` 门禁自身是坏的(显著)**
它把 25 个**磁盘上真实存在**的知识 id 判为"AI 凭空编造"。根因:脚本用 store **目录名**拼有效 id(`team:KT-…`),遥测里用的是 store **别名**(`fabric-team:KT-…`)。`personal` store 恰好别名等于目录名,所以只有它的引用能解析——那就是报告里那 28 条 "resolved"。
更糟的是它的自测只验证"假 id 会被抓",**从不验证"真 id 能解析"**,所以在 100% 误报状态下自测仍打印 `✓ caught`。
放大因素:该脚本不在 package.json / CI / lefthook 中(`docs/TESTING.md` 明确列为手动工具,所以未接线是有意的),**但后果是没有任何东西会发现它坏了**。

复现:

```bash
node scripts/nofake-audit.mjs
```

**F-02 核心契约校验有测试盲区(显著)**
把 `GLOBAL_REF_PATTERN` 的 UUID 段掏成 `.+`(即任意字符串都能冒充合法跨 store 引用),**3310 个测试全绿**。已 rebuild shared dist 后复跑下游,排除假存活。该正则有真实生产调用方 `packages/shared/src/store/cross-store-lint.ts`,也有测试文件引用它——但显然只测了 happy path,没有"畸形 UUID 必须被拒"的断言。

**F-03 `doc-drift-gate` 名实不符(轻微)**
`scripts/doc-drift-gate.mjs:36` 的 `SCANNED_FILES = ["README.md"]` —— 只扫一个文件,`docs/` 下 8 份文档全在范围外。脚本头部注释诚实写明了起因是 README 版本号漂移,所以是命名夸大而非欺骗。

### 2.3 明确的正面项(不能只报坏消息)

- **依赖面极简**:shared 只依赖 `zod` 一个包;server 4 个;cli 8 个。`fastembed` 正确放在 optionalDependencies。这是本次审计**最强的正面项**。
- **分层零反向依赖**:shared 不引 cli/server,server 不引 cli,无循环依赖。
- **基线债已清零**:`typecheck-tests-baseline.json` 内容是 `{}`,没有用豁免名单掏空 typecheck 门禁。
- **测试确实在杀 bug**:变异 M1(倒置 locality 分层)立刻被 3 个测试杀掉,断言钉的是**标定意图**(注释:`same-file locality (100) must lead same-package (25)`)而非常量数值 —— 正合 `KT-GLD-0019` 的规范。对照组 C1(纯标定微调)如期存活,证明套件不是"改啥都红"。

### 2.4 发布稳定性(显著)

83 个 tag 里 **68 个是 rc**,rc/正式 ≈ **4.5 : 1**。`v2.3.0` 一个版本烧掉 **17 个 rc**(约 3 周);`v2.4.0 → v2.4.1` 同日热修。这说明"发布前验证不足、靠 rc 试错"是**稳定模式而非偶发**。

## 4. 要成为"领域最好",最短路径

按投入产出排序:

1. **修 F-01 并给它加反向自测**(小投入,直接收益)。修法:有效集同时索引目录名和别名两种键;自测补一条"随机取一个真实存在的 id,必须 resolved"。这条不修,反幻觉能力等于零。
2. **给 F-02 补负向断言**(小投入)。畸形 UUID / 缺段 / 大小写错误必须被拒。
3. **正面回应"保证 vs 建议"这一问**(中投入,最高战略价值)。要么给出可选的硬阻断模式(哪怕默认关),要么在 README 里**明确论证为什么不做**——现在的状态是内部有决策、对外无说法,读者会默认你没想到。
4. **补首价值闭环**(中投入)。`KT-DEC-0072` 自己已把它列为 D2 待办;"装完就能感知到命中"是把 Fabric 从"作者自用"推向"别人能用"的唯一门槛。
5. **README 增加诚实对标节**(小投入)。把 Basic Memory / Mneme HQ 摆上桌明说各自强在哪。只打裸 `AGENTS.md` 这个稻草人,懂行的读者会立刻扣分。
6. **降 rc 比例**(中投入)。目标是发版前把"本地跑不到、CI 才红"的那类问题堵住。

复核方式:仅读本报告正文、默认立场 refuted、每条判定强制回答"如果错,最可能错在哪"。

| --- | --- | --- |

| "工程有条件完美" | **降级** —— 原措辞暗示 P1 成立就等于"无缺口",但 P1 只覆盖**已有门禁**;F-02 证明门禁没覆盖的地方缺口是存在的。改判为"**优秀但非完美,且缺口总面积未知**" | **已降级** |
| F-01 是显著缺陷 | **保留** —— 根因已用 `has team:… -> true / has fabric-team:… -> false` 直接验证,非推测 | 保留 |
| F-02 是显著缺陷 | **保留但加限定** —— 可能错在:`cross-store-lint.ts` 的调用路径若在生产中从不接收外部输入,则风险等级应下调。**本次未追踪该调用链的数据来源** | **加限定** |
| "rc:正式 = 4.5:1 说明验证不足" | **削弱** —— 可能错在:rc 密集也可能是**刻意的小步快发**策略,而非验证不足。本次**未测量 CI 实际失败率**,该推论仅基于 tag 密度 | **已标为推论,非实测** |

**主评 vs 复核的 gap**:6 条判定中 **3 条被削弱或加限定**(50%)。方向高度一致 —— 被削弱的全部是**推论型**结论(从 tag 密度推验证不足、从对手自述推其能力),而**实测型**结论(变异存活、门禁误报根因)全部站住。

这个 gap 本身是最有价值的信号:**这次审计里凡是自己跑过命令的结论都硬,凡是靠推理和外部文档的结论都软。**
