# Design — Fabric 全项目深审

## 0. 这份设计在解决什么

审计最容易失败的两种方式:①  拿"我觉得"当证据;②  拿一个被自己画好的靶子去证明自己命中。本设计把这两条都变成**流程上做不到**:每条结论绑定可复跑命令,以及领域边界必须先被攻击一轮再使用。

## 2. 评估对象边界

- **In**:`packages/{cli,server,shared}`、`scripts/`、`.github/workflows/`、`docs/`、`README.md`、根 `package.json` 门禁定义。
- **Out**:`~/.fabric/stores/**` 下的知识内容本身(那是数据不是本仓代码)、`.trellis/`(外部框架)、`node_modules`。
- **只读**:全程不修改 in-scope 代码。

## 3. 两条评估轴的方法

### 轴 A —— 领域最佳性

三步,顺序不可换:

1. **Census**:枚举候选全集(agent memory 产品 / rules-file 生态 / 上下文检索层 / 团队知识治理工具链),每个标 in/out + 理由。信息来源用 web 检索,单一来源不下结论。
2. **靶子攻击**(R1 硬要求):对 `KT-DEC-0072` 划的边界做三问 —— ①  这个边界是先于竞争存在的产品判断,还是事后为了让自己成为"唯一"而收窄的?②  按用户真实痛点(而非按此边界)分类,竞争者是谁?③  若边界放宽一档(允许 session memory / 允许编排),Fabric 的相对位置怎么变?攻击结论写进 census 文档,**不允许省略**。
3. **6 轴打分**:问题域契合度 / 生命周期完整性 / 跨客户端可移植性 / 首次到价值成本 / 治理可审计性 / 生态可持续性。每轴给相对位置(领先/持平/落后)+ 一句证据。

**生态轴的诚实处理**:本项目零用户(见既有偏好记录)。生态可持续性不因此得"低分"或"豁免",而是**如实记为"未经外部验证"**,并在最终判定里作为限定条件出现。

### 轴 B —— 工程完美度

"完美"拆成两个可证伪子命题,分开评:

- **P1 门禁下无缺口**:项目自设的所有门禁(build / typecheck / typecheck:tests / lint / test / test:strategy / doc-drift / dangling-refs / store-only-e2e / upgrade-e2e / nofake-audit / red-team-safety / perf-benchmark)**实跑全绿**。
- **P2 门禁本身够严**:门禁没有被基线债、豁免名单、或"只扫得到自己"的口径掏空。

P1 靠跑,P2 靠查。P2 的具体探针:

| 探针 | 手法 | 对应既往教训 |
| --- | --- | --- |
| 测试杀伤力 | 对 3 个核心模块各注入 1 处语义变异,看是否变红;含对照组防等价变异 | `KT-GLD-0019` |
| 基线债规模 | `scripts/typecheck-tests-baseline.json` 当前条目数与豁免面 | 根 `package.json` |
| 门禁自覆盖 | doc-drift / dangling-refs 的扫描口径 vs 宣称口径,含后缀盲区(`.ts`-only 漏 `.cjs`) | 用户既往删词清理教训 |
| 未接线能力 | 抽查若干"有实现有测试"的能力,grep 生产侧调用方 | `KT-PIT-0065` |
| 架构分层 | cli/server/shared 的跨包 import 方向,查反向依赖与循环 | — |
| 发布稳定性 | 从 v2.0.0 到 v2.5.0-rc.4 的 tag/rc 密度,以及 CI 红→绿修复轮次 | 用户既往 rc 烧号记录 |

**工具可靠性约束**:普查类 grep 不用 Bash `grep`(本机是 ugrep,实测有假阴性),统一用 Grep 工具或 node 脚本。

## 4. 独立复核设计(R5)

**用户决定(2026-08-13):不使用外部模型通道**,理由是不希望报告正文离开本机。故复核形态为**本地对抗复核**:主评产出后,以"检方"视角逐条尝试驳倒自己的判定,而非评价好坏。

本地复核的已知强度上限必须在报告中如实写出:`KT-GLD-0006` 实测同一 agent 自评 100% vs 零上下文冷评 81%,gap 全部来自 curse-of-knowledge 式的善意补全。本地复核**无法消除**这个偏差,只能部分削弱。因此 `report.md` 必须带一行显式限定:"未经零上下文外部复核,判定的乐观偏差未被独立消除"。

为尽量逼近冷评,本地复核遵守三条:①  只读 `report.md` 正文,不回看执行过程中的中间证据;②  对每条判定强制写一条"如果这条是错的,最可能错在哪";③  默认立场是 refuted,判定必须自证才能保留。

复核结果三种处置:被驳倒 → 撤回;被削弱 → 降级并标注;未被撼动 → 保留。主评与复核的 gap 单独成节。

## 5. 兼容性 / 回滚

纯只读审计,无回滚需求。唯一写入是 `.trellis/tasks/08-13-*/` 下的文档。若中途发现必须改代码才能验证某结论,**停下来问用户**,不擅自改。

## 6. 明确的非目标

- 不修 bug、不重构、不发版。
- 不对知识库内容(store 下的 KB 条目)做质量评估——那是数据不是工程。
- 不做性能压测调优,`perf-benchmark` 只跑不调。
