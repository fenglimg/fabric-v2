# PRD — 仓库门面整洁化

## 1. 背景与问题陈述

用户原话:「当前仓库其实没有感觉到任何的工程美感,不知道为什么,连看下去的兴趣都没有……
杂乱无章,各个无关紧要文件夹交错其中,一些技术架构也是为了引进而引进的感觉。」

W0-W5 六个批次已经把 `packages/` 内部清得很干净(死代码归零、删 88 份文档、403 个 i18n 死键、
巨型函数分解)。**但那些改善全部发生在「打开文件之后」,而用户的不适发生在「打开文件之前」。**
此前所有轮次的判据都是「这段代码有没有人用」—— 该判据**结构上够不着门面问题**:
`.trellis/` 里每个文件都有人用,`assets/` 里每个文件都合法存在,它们全是「活的」,
但它们共同构成的第一印象是杂乱的。

本任务补的是一条从未被量过的轴: **这个仓库的门面上,有多少东西不是这个产品。**

普查见 `research/surface-census.md`。**普查第一轮推翻了初判**: `.gitignore` 其实写得很好,
`.cursor/` `.agents/` `.codex/` `tmp/` 等全部已被忽略,新克隆根目录是 **25 项而非 34 项**。
因此「杂乱」必须拆成两件独立的事 —— **本机观感**(已忽略的残留,清理零仓库收益)与
**仓库真实结构**(新克隆看到的 25 项)。本 PRD 的主体只治后者。

### 3.1 A4 阈值修订(2026-08-12,用户裁决)

A4 原写「顶层条目 < 40」。**该阈值是在做 import 图分析之前拍的,数据出来后证明它与
design.md「不硬凑目录」的原则不相容**:内聚比检验显示只有 `doctor/`(2.00) 与
`review/`(1.18) 成立,而 `plan-context/`(0.71)、`retrieval/`(0.03)、`ledger/`(0.13)、
`knowledge/`(**0.00**)、`store/`(0.08) 全部不成立。达到 <40 必须建 4 个内聚比近零的假目录 ——
`knowledge/` 那七个文件彼此零引用,这样一个目录名会误导每一个后来的读者。

**裁决: A4 改为 ≤90,只建两个图确认的真组。** 详见 `research/services-clusters.md`。
记录这次修订的原因,是为了让后来者知道 88 这个数字不是妥协出来的,是数据顶出来的上限。

## 5. 非目标 / 明确不追求的

- **不追求根目录条目数最小化本身**。目标是「非产品的东西不要抢产品的格位」,
  不是把所有东西塞进一个目录 —— 后者只是把杂乱藏起来。
- **不追求三个包布局完全一致**。KT-PIT-0080 已论证 server 的测试共址是 `rootDir` 约束下的
  正确选择;R5 的可接受解包含「保持差异但显式写明为什么」。
- **不追求清空本机残留带来的仓库收益** —— R3 只改善用户每天 `ls` 的观感,别人克隆看不到,
  不要把它算进本任务的工程价值里。
