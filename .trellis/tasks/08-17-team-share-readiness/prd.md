# PRD — 组内分享:稳定版本确认 + 上手路径文档

## 1. 目标

让组内同事在**一次分享之后能自己把 Fabric 装上并日常用起来**,不需要回来问我每一步。

这决定了本任务的成败判据不是"文档写完了"或"版本发出去了",而是:**一个没读过任何 Fabric 材料的同事,照着文档能独立走完全流程。**

## 2. 两个交付物

| # | 交付物 | 说明 |
| --- | --- | --- |
| D1 | **v2.5.1 补丁版发到 npm** | 当前 npm `latest` 是 2.5.0,而 main 已多出 8 个 commit(3 个真 bug 修复 + 文档)。同事装到 2.5.0 会带着已知的 worktree 身份解析缺陷 —— 而多 worktree 恰是团队协作最容易撞的场景 |
| D2 | **一份「上手路径」文档** | 把现有 8 篇 docs 收敛成一条从「装」到「跑通第一条知识」的主线;README 给一页入口 |

**明确不做**:不引入 VitePress/Docusaurus 等站点框架,不做部署。理由是组内分享真正卡人的是"装完不知道下一步",不是页面好不好看;站点是持续维护成本,markdown 跟着代码走则是零成本。

## 3. 验收判据

- **AC1(最硬的一条)**:在一个**全新环境**里,从 npm 安装 → `fabric install` → 绑定 team store → 跑通一轮 `fab_recall` + 一次归档,全程不炸。CI 全绿**不能**替代这一条 —— CI 跑的是仓库内测试,不是"陌生人从零装"。
- **AC2**:`npm view @fenglimg/fabric-cli dist-tags` 的 `latest` = 2.5.1,且该版本包含 worktree 身份解析修复。
- **AC3**:文档能让一个零背景同事独立走完 AC1 的全流程;每一个已知失败模式在文档里都有对应的兜底说明(见 §4)。
- **AC4**:同事绑定的 team store 里,他们第一次 `fab_recall` 能拿到有意义的返回(不是空库)。

## 5. 稳定性的判据(为什么是这几条)

同事"要装来日常用"这个选择,把"稳定"的门槛从**演示能跑**抬到了**陌生环境能装能用**。两者差别很大:

- 演示能跑 = 我的机器 + 我的配置 + 我知道绕开哪些坑
- 陌生环境能装能用 = 别人的机器 + 空白配置 + 撞到坑时只有文档能救他

所以验证必须在一个**我没有预先配置过的环境**里做(方法见 design.md),不能在本仓库或本机 `~/.fabric` 上做 —— 那里已经有我攒了几个月的状态,任何"它能跑"都不作数。

- 清理 `wespy-team-cocos-knowledge-base` 的知识内容质量(只处理 pending 数量问题)
- 分享会本身的讲稿/PPT
