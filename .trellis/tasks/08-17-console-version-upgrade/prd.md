# 版本与升级：全机项目版本总览 + 批量重装

父任务：`.trellis/tasks/08-17-fabric-console`
依赖：`console-project-registry`（数据源）、`console-shell`（页面骨架与写通道）

## Goal

一屏看清「npm 上最新是多少、我机器上的 CLI 是多少、每个装了 Fabric 的项目停在哪一版」，并能对落后的项目直接触发升级。

## 为什么需要（实测，非假设）

2026-08-17 本机实测：

| 位置 | 版本 |
| --- | --- |
| npm `@fenglimg/fabric-cli` latest | 2.6.0 |
| 本机全局 CLI | 2.5.0-rc.4 |
| 本 repo `.fabric/install-manifest.json` | 2.5.0-rc.4 |

已经漂了一个 minor，而用户没有任何界面能发现。

且 `docs/UPGRADE.md` 明确写着：升级全局 CLI **不会**自动刷新已安装项目里的 hook 脚本和 bootstrap block，每个 repo 必须重跑 `fabric install`，否则会出现 SessionStart 不注入知识、Skill 不触发等症状。这一步靠人肉记住每个仓库在哪、逐个去跑——正是本子任务要消灭的。

## Requirements

- **R1** 总览三个版本：npm latest、本机全局 CLI、各已注册项目的 install 版本。
- **R2** 落后的项目高亮，一眼可辨。
- **R3** 对选中项目触发重跑 `fabric install`。
- **R4** 升级过程的输出对用户可见，不是黑箱转圈。
- **R5** stale 项目（路径已失效）明确区分于「落后」，不要混在一起让用户以为是待升级。
- **R6** npm latest 查询失败（离线 / 网络问题）时页面仍可用，降级为只显示本地信息并说明原因。

## Constraints

- **C1** 升级动作调用既有 `fabric install`，不复制安装逻辑。
- **C2** 「怎么算落后」的判定逻辑落在内核并被 CLI 与控制台共用，UI 不自己算——否则会出现界面说落后、CLI 说没落后的分叉。
- **C3** 升级是有副作用的操作，执行前需用户在界面上明确确认，不得因误点直接改动多个仓库。
- **C4** 批量升级中单个项目失败不得中断其余项目，且失败项要如实报出——不能只报成功数。
- **C5** 不自动升级。用户没点，什么都不发生。

## Acceptance Criteria

- [ ] AC1 页面同时显示 npm latest / 全局 CLI / 各项目版本，与命令行实测值一致。
- [ ] AC2 版本落后的项目有明确视觉区分，stale 项目与落后项目视觉上可区分。
- [ ] AC3 对一个落后项目触发升级，完成后该项目 `install-manifest.json` 的 `fabric_version` 与全局 CLI 一致。
- [ ] AC4 升级过程中界面能看到进展或输出，结束后有明确的成功/失败结论。
- [ ] AC5 断网状态下打开页面，本地信息正常显示，npm latest 一栏明确说明获取失败。
- [ ] AC6 批量升级中人为让一个项目失败（如目录只读），其余项目仍完成，且失败项被如实列出。

## Out of Scope

- 升级全局 CLI 本身（`npm install -g` 属于用户的包管理器动作，不由控制台代劳）。
- 版本回滚 / 降级。
- 跨机器同步。

## Notes

- 项目发现方案：install 时登记（用户决策）。存量项目需各跑一次 install 才会出现在列表里——首次使用时列表可能不全，页面应说明这一点，而不是让用户以为「我只有这几个项目」。
