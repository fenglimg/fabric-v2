# State Placement Thinking Guide

> **Purpose**: 在写下一个新文件、新配置字段、新缓存之前,先想清楚它该住在**全局(`~/.fabric/`)、项目(`<repo>/.fabric/`)还是 store**。放错层的代价不是"不好看",而是"看得见的值不是生效的值"——本仓最难排查的一类 bug。

---

## 这份指南与 `KT-MOD-0004` 的关系

`KT-MOD-0004`(配置 key 单一可写位置)是**本指南的核心**,不是并列的另一套规则。

- `KT-MOD-0004` 回答的是:**一个 config key** 该归哪层(身份归 project、人的偏好归 global、知识库属性归 store),判据是"给这个 key 设跨实例默认值有没有意义"。
- 本指南做两步推广:
  1. 从 **key** 推广到 **物件**(文件、目录、安装副本、缓存);
  2. 补上 `KT-MOD-0004` 不覆盖的**数据层**(运行时产生、会持续累积的东西)。

推广而非新立。任何时候两者的结论冲突,以 `KT-MOD-0004` 为准。

---

## 判据一:物件层 —— 看「正确版本由谁决定」

问一句:**这个东西的"正确版本"是谁说了算?**

| "正确版本"由谁决定 | 归属 | 本仓实例 |
| --- | --- | --- |
| 这台机器上装的 Fabric 版本 | **全局** | hooks / skills / templates 的内容 |
| 这个仓库 | **项目** | `project_id`、store 绑定、启用开关 |
| 知识库自己 | **store** | corpus 参数、知识性质字段 |

反过来用更好使——**放错层的症状**:

- 该归全局却放项目 → 升级 CLI 后 N 个仓库各自持有 N 份陈旧副本,且没人知道哪份是新的(本仓的 `install_copy_drift` 检查就是在追这个)。
- 该归项目却放全局 → 需要一张 `路径 → project_id` 的反查表;而 `KT-PIT-0050` 实测过:binding 快照里**根本没有 repo 路径**,这张反查表在系统中不存在。别去造它。
- 该归 store 却放项目 → 每个绑定该 store 的仓库都能改同一个知识库属性,谁最后写谁赢。

### 已知的例外(记在这里,免得反复重推)

`fabric install` 往每个项目写的 138 份副本(hooks 40+40、skills 29+29,源 71 份),**按判据归属是全局**——它们的正确版本由 CLI 版本决定,不由仓库决定。但当前**刻意不搬**:

客户端的 hook 配置只认仓库相对路径(`${CLAUDE_PROJECT_DIR}/.claude/hooks/*.cjs`),搬去全局需要引入一层 shim 间接。而本项目自身的开发环路已经受"全局装的 fabric 遮蔽本地源码改动"的困扰,再加一层间接会放大它。

**判据先立,搬家另议。** 引用本条时请连同这个理由一起引用,别把"不搬"读成"判据不适用"。

## 判据二:数据层 —— 看「天然聚合边界」

运行时产生的数据不问"谁说了算",问:**它天然按什么聚合?**

| 天然按什么聚合 | 归属 | 附加要求 |
| --- | --- | --- |
| 按 repo | 项目 | — |
| 按人 / 按机器 | 全局 | — |
| **按 session** | 两边都不该长期堆积 | **必须有 TTL 或随 session 生命周期回收** |

第三行是最容易漏的:per-session 文件写下去的那一刻看着很小,没有回收就是单调增长。写之前先回答"谁来删它",答不上来就先别写。

参考:`.fabric/.cache/` 下的 per-session sidecar 就属于这一类,回收由 `doctor` 的 stale-hints 清理承担——**新增一个同性质的文件前缀时,必须同步登记进清理器的前缀集合**,否则它会成为一个没人回收的孤儿分支。

## 判据三:worktree 不是一个新项目

一个 repo 的多个 worktree **共享同一个 project 身份**,不是各自独立的项目。

理由很朴素:`.fabric/fabric-config.json` 是 **tracked** 的,所以 `git worktree add` 天然把 `project_id` 带过去。**git 本身就是分发机制。**

推论:

- 身份解析是 **local-first** —— checkout 自带 config 就是它自己的 identity root,不去查仓库拓扑;
- 只有"早于 `fabric install` 的 checkout"才走继承(冷路径),且继承源必须问 git 要(`git worktree list --porcelain` 首条记录),而不是从路径 basename 上猜;
- 猜不出来就**明确失败**并告诉用户跑 `fabric install`,不要编造一个 identity root。

历史教训:旧实现用 `basename(commonDir) === ".git"` 猜主仓库。这个判据对 bare 托管布局(`foo.git` / `.bare` / `<container>/.git`)会指向一个**根本不是 checkout 的容器目录**,而且它**永远不会抛错,只会误导**——在 3310 条测试全绿的情况下活了很久。

> **通用教训**:当你要为"某个东西在哪"写一段启发式推断之前,先确认底层工具是不是已经权威地回答了这个问题。git 会告诉你主 worktree 是谁;自己从路径上猜,只是给自己造了一个不会报警的错误源。

## Quick Reference: 触发时机

新增以下任何一样东西之前,过一遍本指南:

- [ ] 一个新的配置字段 → 判据一 + `KT-MOD-0004`
- [ ] 一个 `fabric install` 会往项目里写的文件 → 判据一(注意上面那条例外)
- [ ] 一个运行时写盘的缓存 / sidecar / 计数器 → 判据二,**先回答"谁来删它"**
- [ ] 任何 per-session 命名的文件 → 判据二第三行,同步登记进清理器
- [ ] 任何需要"从路径推断出身份"的逻辑 → 判据三,先问 git

## 反向自查

- 这个 key/物件有没有**第二个地方也能写**?(有 → 违 `KT-MOD-0004`)
- 我是不是在造一张**反查表**来弥补放错层?(`KT-PIT-0050`:路径反查表不存在,别造)
- 我写的这段推断,**失败时会不会抛错**?只会给出"看起来合理的错答案"的推断,是最贵的一种。
